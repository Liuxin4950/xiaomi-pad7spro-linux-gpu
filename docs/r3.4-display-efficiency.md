# r3.4 显示链路迭代：r3.4.2 独立候选

2026-10-13。当前默认仍为 r3.4.1 damage-coalescing-1，r3.3 完整保留。本页描述已实现的候选功能与待验收边界，不能作为已降低延迟或功耗的结论。

## 实现范围

本轮按用户要求先完成显示效率的技术迭代，再统一验收。原厂 Mali、Skia GaneshVulkan、ANGLE Vulkan、Zink 和现有颜色/同步契约保留。

代码审查确认：WSI 在 Present 前使用独立单调时钟限帧，FIFO 又等待 X11 Complete；现有 X11 已用 Choreographer 门控 MSC/redraw，但会持续请求每个 VSync，空闲也有 5 秒统计定时器。两套控制是否恶化最终 P99 尚未测定，不能单凭代码认为发生性能回退。现有 renderer 通过状态与条件变量等待，并非静止时必然持续画全屏。

### 显示时钟协商与队列约束

[WSI 补丁 0008](../patches/wsi/0008-display-clock-pacing.patch) 与 [X11 补丁 0004](../patches/termux-x11/0004-demand-driven-display.patch) 构成一个功能。

X server 在 root 发布 `_TERMUX_X11_DISPLAY_CLOCK`，CARDINAL/32、三项 `[协议版本=1, 显式 max-fps, 能力位]`。能力位 1 是 Choreographer 时钟，2 是 target-MSC 按 Choreographer 节拍调度，4 是按需回调。只认精确长度、已知版本、1–240 FPS、至少前两位，且服务器上限不高于用户 WSI 上限。

协商成功后，WSI 使用自身请求的 X11 Complete 唤醒，取消独立 Present sleep；同一 swapchain 至多一个下游请求在等待 Complete。MAILBOX 也使用这一约束，阻塞发生在既有可阻塞 Present 路径；没有宣称实现跨进程“只保留最新帧”丢弃协议。下一目标 MSC 来自 Complete 的 MSC 与模式：历史 0008 错把 Copy 下一目标设为 MSC+2；锁定 Xorg 实际只有同步 Flip 在 exec_msc 上减 1。0009 已将 Copy/Flip 下一目标统一修正为 Complete MSC+1，纳入独立 r3.4.3/r3.5。Skip 会恢复 timer，避免遮挡/跳过时快速循环。Complete 可能早于屏幕显示，不能把它称为 VSync 或 scanout。Idle 仍只负责释放 consumer buffer，不能替代 Complete。

旧 X11、未知协议、畸形属性、服务器上限高于用户上限时，都保留原来的 timer 限帧。`PAD_GPU_PRESENT_CLOCK=timer` 可单应用回退，默认 `auto` 只是请求协商；不会仅凭 RandR 数字取消限帧。连接当前 APK 的候选会走兼容路径。用户设置更低的 WSI 上限时仍使用 timer，没有擅自放宽上限；显式 WSI 上限 0 保留原来的无 WSI 限帧契约，不启用新协商。

### 按现有更新事件请求 VSync

有显式 `-max-fps` 的新 X server 在自己的 BlockHandler 检查现有 root Damage、光标更新、drawRequested、GPU copy 队列和待完成 vblank。只有存在工作时才请求下一次 Choreographer 回调；回调没有自我永久重新注册。一个 callback 和一个 server work item 分别去重，输入与 GPU 完成事件继续通过现有队列处理。

逻辑 MSC 由同一单调时间基准按节拍推导，跨越空闲后直接前进；不会为补数回放几百个旧 tick。vblank 通知仍在有效 Choreographer tick 执行。无显式上限时保持旧的连续 MSC 行为。Surface 恢复通过已有 GPU 完成通知通道唤醒 X server，即使尺寸没变也重新请求首帧，避免依赖下一次输入。默认关闭 5 秒统计 timer；`TERMUX_X11_DEBUG` 保留它供诊断。

没有新增全屏哈希、图像相等判断、固定 10/30 FPS 空闲降帧，也没有将空增量列表当作“无变化”。r3.4.1 的所有轮换 AHB damage 修复、局部复制和 fence 保留。

### 帧关联与搬运诊断

诊断依旧默认关闭。WSI 通过已有 `PAD_GPU_WSI_TIMELINE_DIR` 输出有界事件，增加 timer/display wait、协商频率、Complete 的 UST/MSC/mode；`payload_begin` 带 VkImage，`x11_request` 绑定 pixmap、serial 与 payload_sequence。探针 CSV 同时记录 render_image/image_index，可按图像与提交顺序连接应用帧和 WSI。

APK 使用 Perfetto/atrace 按需启用标记：

| 事件 | 关联内容 |
|---|---|
| InputDispatch | Linux X11 输入分发区间；不是硬件触摸采样时间 |
| Tick | MSC 与 Choreographer 单调时间戳 |
| PresentFlip | X11 pixmap、client serial、AHB/root buffer ID |
| PresentCopy | X11 pixmap、client serial、内部 copy serial |
| CopyEnqueue / CopyIssued | copy serial 与 source buffer ID |
| CopyPixels | 实际复制矩形像素预算，不是 DRAM 带宽 |
| CopyBatchIssue / CopyAndRootFenceWait | CPU 发指令与合并 copy/root fence 等待区间 |
| CopyDone | GPU fence 完成后的 copy serial |
| SurfaceSubmit | copy serial、root buffer ID、可用时的 EGL frame ID |
| SurfaceTime | 可用的 queue/render/latch/display-present 时间及 EGL frame ID |

Surface 时间依赖 [EGL_ANDROID_get_frame_timestamps](https://registry.khronos.org/EGL/extensions/ANDROID/EGL_ANDROID_get_frame_timestamps.txt)。仅诊断时启用，最多保留 16 个未完成帧，复用下一次实际绘制查询，不创建空闲轮询线程。不支持、负值、pending、历史淘汰都不记为真实呈现样本；最后静止帧的 pending 时间可能尚未收集。

WSI 原有 GPU timestamp queries 量化 transfer/barrier 窗口；producer-ready fence 时间含应用渲染与调度，不能叫纯 Copy 时间。X11 合并 fence 含 Copy 和 root draw，同样不能叫纯 Copy GPU 时间。多个窗口可能被合并进同一 Surface；对应的是一批 copy，而非一对一应用帧。

[Perfetto FrameTimeline](https://perfetto.dev/docs/data-sources/frametimeline) 对 SurfaceView 的数据覆盖有局限。本路径同时准备 EGL 时间与 SurfaceFlinger latency 辅助数据；不能靠最近时间戳硬配对，更不能把 X11 Complete 当成物理屏幕显示。

## 完整链路验收与部署

桥接与 APK 必须共同验收。APK 替换后旧 X server 仍可能映射旧代码；重复点击应用不能证明升级。正常重开桌面会结束 chroot 会话，因此需先保存全部工作，按 [AGENTS 第 7 条](../AGENTS.md) 操作。

准备好会话后，再安装保存了签名/原件的 candidate.apk，正常重开桌面并核对新 X server/APK 映射及 root 能力属性；随后用同一候选探针、同一新 APK，在 r3.3、候选 timer、候选 auto 间交替至少三轮。APK 空闲改动还需与保留的原 APK 做单独对照；同一新 APK 上的桥接 A/B 不能证明 APK 自身的 CPU/功耗收益。

[profile-display.py](../scripts/profile-display.py) 已更新为当前前缀、交替轮次、原生尺寸、前后亮度/刷新率核对，默认没有第三个独立 producer sleep。`--trace` 才启用 GPU timestamp 与帧事件；auto 协商为 0 时会明确标记显示时钟验收未就绪。

```sh
python3 scripts/profile-display.py --output build/display-ab --runs 3 --seconds 10
python3 scripts/profile-display.py --output build/display-ab-traced --runs 3 --seconds 10 --trace
```

Perfetto 配置：[perfetto-display.cfg](../reference/perfetto-display.cfg)。分别记录静止、仅光标/光标闪烁、滚动输入三种负载；用调度事件计数线程唤醒与 CPU，用帧 ID/可靠呈现时间计数新内容，用既有 sampler 记录放电状态、电流、电压及温度。60/120 Hz 对照须核对实际面板模式和 X11 上限，不只改 WSI 数字。诊断开销与正常运行分开测量。

输入延迟需要实际输入事件到对应响应图像的因果标记；InputDispatch 或 P99 帧间隔都不能代替端到端输入延迟。电池计数器是整机指标，能力与精度取决于设备，见 [Perfetto power](https://perfetto.dev/docs/data-sources/battery-counters)。短窗、充电样本、温度尚未稳定或条件发生变化时不宣布省电。

## 保留的后续工作

r3.4.1 已减小 WSI 局部 Copy，但未将 damage 传到后半段 X11 Present；此处仍按完整/可见窗口区域搬运。先用新增诊断确认耗时、次数及区域，再决定是否改 consumer 内容历史与 expose 行为。没有直接 AHB 渲染或零拷贝实现，没有删除 producer fence、consumer Idle 或 swap 后兼容操作。

视频解码、WebKit SHM、真实 Chromium/Electron 主线程热点属于独立专项；本轮没有 MediaCodec 桥接。长期 Trae/Chromium、中文输入、多窗口、锁屏恢复、持续温升与整机能耗尚待共同验收。正式完成标准仍是实际显示 P95/P99 不恶化、响应性改善或 CPU 时间降低、空闲没有可避免高负载，并保持应用稳定。

回退可独立进行：单应用 `PAD_GPU_PRESENT_CLOCK=timer`；完整桥接退回已保留 r3.4.1 或 r3.3 并重开应用；APK 恢复保存的 original.apk 后正常重开桌面。文件不能热替换已映射代码。

部署后运行状态已更新至 [整链路结果](r3.4-display-results.md)。本页“未安装/未重启”表述属于候选构建完成时的历史快照；实际是否保留新 APK 或自动回退，以结果中的实装哈希为准。默认桥接未自动推广。
