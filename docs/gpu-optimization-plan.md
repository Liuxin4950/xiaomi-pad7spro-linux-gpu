## 2026-10-16 鼠标交互与 120 FPS 专项

本节更新优先级，后面的 2026-10-15 基线、已完成项目和历史结果保留。用户此次明确选择 120 FPS，覆盖原计划“默认 60、120 仅可选”的约定。目标是先解除现有限制，再只处理有证据的热点，不重新开展整个架构升级。

**本次已交付配置**：仓库与实装 gpu-run 默认 PAD_GPU_MAX_FPS=120；Termux 实际 desktop-zink.sh 与参考文件同步，X11_MAX_FPS/PAD_GPU_MAX_FPS 均默认 120，普通桌面/Widget 继续转发。profile-display 默认 120，可显式传 --fps 60 做对照。历史 benchmark-wsi 固定 60 的旧版对照及历史 CSV 不改。显式环境覆盖仍被尊重，不改用户参数。

**生效边界（重开前历史）**：当时运行中的 X11 启动参数是 -max-fps 60，根窗口协商属性是 [1,60,15]，RandR 约 59.96 Hz。Android 显示模式自那时起为 120.00001 Hz，peak_refresh_rate=120。源码 maxFramerate 只由启动参数赋值；修改 RandR 或只伪造根属性不能解除内部节拍限制。完整生效须用户保存工作后正常重开桌面。没有实测全链 120 FPS 或新的节能结论。

**2026-10-16 重开后运行核对（步骤 1 已完成）**：用户已用 zink 脚本正常重开桌面，配置在运行态生效。实测：X11 参数 `-max-fps 120`；根窗口 `_TERMUX_X11_DISPLAY_CLOCK = [1, 120, 15]`；Android 模式 1（120.00001 Hz）；SurfaceFlinger 该图层测量周期 8.333 ms。小窗口探针在**不加采样工具**时 3000 帧平均 80.1 fps，图层呈现间隔中位数 8.58 ms（约 117 fps），实测约每 6–9 帧出现一次 25–30 ms 停顿把平均拉低；三个并发客户端合计提交 257.6 fps，说明当前限制不是全链吞吐上限。仅移动光标的窗口内该图层按 8.43 ms 间隔（约 118 fps）连续呈现，X 服务端 CPU 从 79 升到 161 ms/s。Mali 不是该样本的瓶颈（拷贝批次 p50 2.06 ms、交换 p50 0.57 ms、就绪等待低于 0.1 ms）。活动时钟、timer 时钟与 mailbox 三种模式的单客户端帧率都在 78–84 fps。

**采样条件警告**：开启 atrace（gfx/view/sched）并每秒 dumpsys 采样时，同一负载只有约 38–40 fps，服务端回调被拉长到 p50 24 ms；这些数字描述的是采样条件，不能当作正常使用帧率，也不能用它们判断 Mali 是否到极限。两种条件的数据都保留在 [运行诊断证据](../evidence/fps120-runtime-diagnosis-2026-10-16.json)。

**修订后的下一步**：不再把"是否 120"当作待测项；剩余问题是长尾停顿的归因与光标路径的效率。顺序调整为：① 用不干扰采样的方式（按需短采样、X 服务端自身计数）定位 25–30 ms 停顿来源，区分 X11 串行回路、周期空重绘与桌面其他客户端争用；② 只在归因成立后再做最终 Surface 的局部/光标优化（T6 候选），并保留整幅绘制回退；③ 空闲唤醒审计继续按原 T4 进入条件执行，不新增常驻机制；④ 收益与功耗仍用 120 对 120 的同工作量比较。

本次最小运行检查（重开前、且开启采样工具，保留为条件记录）：隔离 640×480 Mali 窗口请求 WSI 120、X11 仍为 60，360 次客户端提交完成；整个 Termux:X11 Surface 短样本约 40.03 次呈现/秒，间隔 P50 24.99 ms、P95 41.65 ms。它混有其他应用活动，不能等同用户页面 FPS、屏幕新内容 FPS 或输入延迟；也不能由该样本认定具体节拍 bug。静止探针仅提交一帧且后续探针 CPU 为 0，但共享 X11 仍有开销，不能声称整个桌面已空闲。两项检查正常退出并确认 Mali 映射。同一负载在关闭采样工具后测得约 80 fps；两组数字不能互换。数据见 [本次证据](../evidence/fps120-2026-10-16.json) 与 [运行诊断证据](../evidence/fps120-runtime-diagnosis-2026-10-16.json)。

**已确认的剩余开销**：本次核查最终编译源码 `build/optimization-20261015/x11-repro-labelled/source/lorie/src/main/cpp/lorie/renderer.cpp`：1195/1253 行的光标 moved/updated 会触发绘制；1111–1157 行关闭 scissor、整幅清屏、绘制 root texture，再画光标、同步并 eglSwapBuffers。因此仅移动光标也会进入整幅 Surface 绘制。现有 WSI/X11 局部复制不能消除这段工作。这个事实足以进入定向优化评估，但尚未证明它是卡顿的唯一原因或能节省多少瓦。

## 1. 目标与取舍

目标是让日常网页、代码编辑、桌面交互中适合硬件执行的绘制、合成与搬运尽量由 Mali 承担，同时保持画面正确、交互流畅、空闲安静、能耗可控，且能够从明确的源码和依赖重新部署。

不把“全部 GPU 化”作为验收口号。JavaScript、布局、业务逻辑、部分解码和传统 CPU 绘制仍会存在；强行把低成本工作搬到 GPU 可能增加传输、同步和功耗。视频解码由媒体硬件能力另行验收，不等同于 Mali 图形加速。

取舍顺序：**数据与会话完整、像素与同步正确 → 可恢复和可复现 → 日常应用覆盖 → 实测流畅度与能耗 → 高风险架构探索**。同样收益时，选择改动更小、上游接口更稳定、依赖更少的实现。只有能解释成本和收益的优化才进入默认路径。

先完成现有架构的交付闭环，不为版本号增加功能，不承诺未知的帧率、瓦数或节能百分比。测不到的结果标记未确认，不通过降低分辨率、降低画质、吞帧、冻结程序或软件回退制造改善。

| I1 | 单应用启动参数、诊断工具、独立安装前缀 | 优先；有明确开关，不改变其他应用的环境 |
| I2 | WSI、Termux:X11、入口安装、设备侧用户空间适配 | 有热点或正确性证据才做；独立候选、能力协商、整套回退 |
| I3 | WebKit 专用构建、媒体服务、新共享缓冲协议、长期应用 fork | 条件性原型；先证明需求、兼容与维护成本 |
| 禁止项 | 系统分区/SELinux/原厂驱动修改，冻结系统服务，全局 kill，关闭温控 | 本计划不包含这些操作；不把 root 当成绕过正确命名空间的办法 |

可移植目标按层交付，不能从一台设备成功推导“所有 Mali 都支持”：

1. **R0：本机干净复现。** 相同固件，新的构建目录与独立前缀，不依赖旧 canary 或历史对象。
2. **R1：本机新 rootfs。** 从依赖清单恢复运行环境，入口、挂载与配置可重新安装，保留原 rootfs；先验证兼容的 arm64 Debian 环境，不同时扩大所有发行版。
3. **R2：相同机型其他固件。** 重新探测 HAL/ABI、AHB 格式、同步、binder、EGL 能力；无实机即标记未测试。
4. **R3：其他 Mali/Android 设备。** 只复用接口和能力探测，不默认支持；必须独立设备验收。跨桌面 CPU 架构不是当前承诺。

AHB 可以共享不等于标准 Linux GBM/DRM 可用；Android binderfs 必须来自正确的 Android 实例，不能只依赖 root 或一个 `binder_logs` 目录名证明连接正确。旧检查可保留兼容，但探针应验证实际所需服务/分配动作，并报告失败阶段。

运行环境与构建环境分开：已构建前缀因 RUNPATH/manifest 固定，不能直接改目录名；第一阶段保持现有 `/opt/<独立前缀>` 契约，通过指定目标前缀重新构建实现迁移，不把“任意移动二进制目录”列为必做重构。

## 4. 执行顺序与规模

S 为一个局部模块；M 为多个相关模块；L 为跨进程或跨工具链。它们表示相对规模，不是交付日期。

| 编号 | 工作包 | 类型/优先级 | 侵入/规模 | 依赖 |
|---|---|---|---|---|
| T0 | 当前状态与改动基线整理 | 必做 P0 | I0–I1 / S | 无 |
| T1 | 构建复现与能力发现 | 必做 P0 | I1–I2 / M–L | T0 |
| T2 | 可信测量与最小工作负载 | 必做 P0 | I0–I1 / M | T0；能力字段复用 T1 |
| T3 | 生命周期、错误路径与真实交互 | 必做 P0 | I1–I2 / M | T1、T2 |
| T4 | 空闲、后台与恢复效率 | 有证据优化 P1 | I2 / M | T2、T3 |
| T5 | 帧节拍与排队延迟 | 有证据优化 P1 | I2 / M | T2、T3 |
| T6 | 最终 Surface 局部绘制 | 条件性优化 P1 | I2 / M–L | T1–T3；实测热点 |
| T7 | 格式、复制与直接 AHB | 条件性原型 P2 | I2–I3 / L | T2、T3；T6 结果 |
| T8 | 应用覆盖与 WebKit | 基础覆盖必做 P1；深改 P2 | I1–I3 / M–L | T1–T3 |
| T9 | 视频硬解 | 条件性原型 P2 | I3 / L | 视频需求与 CPU 热点证据 |
| T10 | 能耗、资源与长时验收 | 必做 P1 | I0–I1 / M | 所选候选功能完成 |
| T11 | 可恢复部署与完整交付 | 必做 P0/P1 | I1–I2 / M | T0 先设计；T3/T10 后推广 |

默认顺序：T0 → T1/T2 的最小闭环 → T3 → T4/T5 中测出的主要问题 → T6 能力和热点判断 → T8 基础覆盖 → T10 → T11。T7、T8 深改、T9 单独作进入决定，不阻塞主线交付。

允许不同 AI 分别承担源码复现、离线证据分析、独立模块开发；**同一台设备的 APK 切换、系统入口、桌面会话和性能采样必须串行，由一个集成执行者负责**。不同模块用不同提交/候选，不在共享目录并行修改同一补丁和 sources.lock。

- 区分“同源码可重建且功能相同”和“字节级可复现”。先完成前者；后者再处理时间戳、归档排序、build ID、绝对路径、签名等差异并报告，不虚称 APK 哈希必然一致。
- 私有 bionic 仍是固定二进制依赖；不能宣称全链从公开源码重建。原厂驱动从设备挂载读取，不打进发布包。

### 能力发现与配置

- 扩展现有 doctor/info/probe 的结构化输出，优先重用现有命令，不增加常驻监控服务。普通 doctor 保持只读前置检查，创建 GPU/窗口的主动探针必须显式区分。
- 报告：设备/固件、Android API、arch/page size、Mali/Vulkan、AHB 各 format/usage/tiling 查询结果、真实分配/导出/导入结果、WSI/X11 协议能力、实际 EGL 扩展、显示模式、可用测量节点。
- 能力查询失败时不读取未定义的输出字段；某种 usage 查询成功不能推广到其他 usage。EGL 探测必须来自实际 renderer 的 display/context，不能用另一进程或另一驱动的字符串替代。
- rootfs、Termux home、UID/GID、DISPLAY/runtime、Android 命令入口允许显式指定或从已有环境解析；保留本机默认。优先调整已有参数，不先发明通用配置数据库。
- `gpu-run` 只给目标应用所需变量；不污染 TUI/MySQL，不把 WebKit 改成 Electron 参数，不强制改 locale、HOME 和全局工具包后端。未知环境输出“未支持/需验证”，不静默切软件。

验收：同固件、全新工作目录可构建独立候选；另一个干净 rootfs 能按文档安装到指定前缀并通过核心探针。无第二环境时如实保留 R1 未确认。设备能力不支持的可选优化保持现有硬件路径；核心能力缺失则明确失败。

## 7. T2：让测量能支持工程决策

入口：`scripts/profile-display.py`、`scripts/sample-gpu.py`、`scripts/system-cpu-sample.py`、`scripts/benchmark-wsi.py`、`src/probe-present.c`、现有 timeline/atrace、`reference/perfetto-display.cfg`。

7. 所有日志有容量/时长上限，默认关闭；不新增空闲轮询线程。每个结果包含正常/诊断模式、环境变化和无效原因。

输入延迟先用测试页面/窗口把输入事件编号编码到响应帧，再关联输入分发、应用响应、Copy 与可靠呈现时间；软键盘、触摸、鼠标各自标明起点。跨进程使用同一可校验时钟域，MONOTONIC/BOOTTIME/REALTIME 不直接相减；休眠、时钟偏移变化和无法关联的样本剔除并计数。高帧率相机等物理测量设备不可用时，保留软件可观测延迟，不推算光子延迟。

建议只保留六类可重放场景：无窗口桌面静止；应用静止（另分光标闪烁）；小范围文字/局部动画；固定长页面滚动；代码输入+中文候选框+菜单；窗口遮挡/resize/前后台恢复。视频单独纳入 T9。优先用离线固定页面和现有 probe，不复制用户登录 profile。

验收：工具能拒绝不存在的候选和无效样本，能报告而不是掩盖采集失败；相同版本 A/A 的噪声量级已知；实际运行版本、应用窗口 readiness 与采样窗口正确。Trae target 等待条件需检查窗口/target 就绪及超时，工具时序失败不能写成 GPU 崩溃。

测量接口依据：[Perfetto FrameTimeline](https://perfetto.dev/docs/data-sources/frametimeline) 与 [power counters](https://perfetto.dev/docs/data-sources/battery-counters)。数据源覆盖和单位在目标设备上确认，不能仅凭接口存在推导数据完整。

## 10. T5：呈现节拍与排队

入口：WSI 0008/0009/0011，X11 0004，`test-frame-pacing.c`，现有 FIFO/MAILBOX 路径。

进入条件：发现重复等待、长尾、请求积压、SKIP 后长期错误回退或模式切换异常。当前“每 swapchain 最多一个等待 Complete”的机制已存在，先验证。

执行：

- 记录协商请求与实际选择；确认 auto、显式 timer、旧 APK、低于服务器上限的用户限帧和 0 上限各自契约。
- 用同工作负载区分应用生产慢、WSI 等待、Copy、EGL/Android 排队。60 Hz 时间预算约 16.67 ms，120 Hz 约 8.33 ms，只是预算，不能把 Complete 当屏幕 VSync。
- 针对证实的问题修正 MSC/时钟/恢复状态；跨空闲、时钟异常、59.94/119.94 等非整数节拍与抖动由纯时序测试覆盖，不要求本机具备所有模式。
- 多窗口验证公平性与总开销。每链上限不是全桌面总帧率；若总队列确实拥堵，优先修现有队列背压/唤醒，禁止先引入全局调度服务。
- 不为低延迟删 fence、不扩大无限队列、不默认增加 swapchain 图像数。不把“仅保留最新帧”用于未定义丢弃语义的协议。

验收：指定上限被遵守，恢复后能正确协商，队列有界且不饥饿；P95/P99、最大停顿、相同工作量 CPU 及输入响应与基线比较。若只降低 CPU 但增加可感知延迟，不默认推广。2026-10-16 用户已明确将默认改为 120 FPS；60 FPS 保留作显式对照，仍需测功耗与真实屏幕模式。

## 11. T6：最终 Surface 局部绘制——优先评估的剩余方向

入口：实际 Termux:X11 `renderer.cpp` 的 `redrawLocked`/root draw/eglSwapBuffers 路径、X11 0004/0005、现有 CopyPixels/SurfaceSubmit 诊断。

假设：WSI 与 X11 Copy 已局部化，但最终 root texture → EGL Surface 仍可能每次绘制全屏。如果这里占显著 GPU 时间/搬运预算，局部绘制可能比继续压缩前段微小开销更有价值。**尚未证明其为当前瓶颈，也未确认目标 EGL 能力。**

执行分三步：

1. 在最终编译源码中确认 root draw 实际范围、光标/缩放/平移/viewport 的影响，读取真实 EGL 扩展、buffer age 与失败行为；测出完整重绘的成本。
2. 先用当前完整绘制路径验证 damage 向最终 Surface 的正确传递；然后才做 buffer-age 驱动的局部重绘原型。区分本次 surface 变化区域与特定后缓冲需要修复的区域，两者不能共用一个错误列表。Khronos 对此有明确区分。[partial_update 规范](https://registry.khronos.org/EGL/extensions/KHR/EGL_KHR_partial_update.txt)
3. 必须处理缓冲 age=0、历史不足、resize、Surface 重建、上下文丢失、色彩/旋转/viewport/缩放变化、光标旧新位置、未知 damage。历史无效恢复全量；按正确坐标与采样范围转换，双线性缩放需覆盖滤波边界。只在支持且实测正确时使用相关 EGL 接口。[buffer_age 规范](https://registry.khronos.org/EGL/extensions/EXT/EGL_EXT_buffer_age.txt)

新功能使用显式候选开关；能力缺失或调用失败回到现有全量 GPU 绘制。不要强制 EGL_BUFFER_PRESERVED、不要在绘制之后补设 damage、不要未经 buffer 内容保证就简单加 scissor。Swap-with-damage 提示本身不保证驱动减少所有物理搬运。

验收：多缓冲轮换、连续局部变化、光标、缩放、菜单、恢复各自像素正确；局部场景 GPU 工作量/耗时出现可重复下降，完整滚动不显著退化；资源和空闲行为不恶化。扩展不可用、收益不明确或维护成本过大时，保留完整绘制并关闭此任务，不能伪称已支持。

## 12. T7：格式与直接 AHB，避免盲目追求零拷贝

入口：`src/probe-vulkan.c --ahb-formats`、AHB wrapper、WSI image 创建/bind/payload/copy、X11 drawable/pixmap 格式和 renderer 采样路径。

当前已知：本机既往 RGBA8 AHB attachment 查询成功，相应 BGRA8 查询失败；应用公共 BGRA 图像和私有 RGBA AHB 有现存字节契约。普通 RGBA 路径已经具备直接导出的部分能力，不能重复开发并称“全链零拷贝”。

进入条件：T2 证明必要复制仍占主要开销，并且 T6/局部更新已经不足以解决目标场景。

先扩展精确格式矩阵，覆盖真实 format/usage/tiling/import/export/dedicated allocation、alpha、sRGB/UNORM、同步与多缓冲；逐步实测，不能用扩展字符串代替可分配/可导入证据。[AHB 外部内存规范](https://docs.vulkan.org/refpages/latest/refpages/source/VK_ANDROID_external_memory_android_hardware_buffer.html)

原型优先次序：

1. 对实际使用 RGBA 且消费者兼容的应用验证现有直接路径，量化是否真的少一道 Copy。
2. 只有两端能明确协商时再研究统一格式/采样通道契约；保持未参与协商的 BGRA 应用、X11 visuals、截图和读回正确。
3. 全屏直接呈现/绕过 root copy 仅作为独立探索：必须覆盖遮挡、菜单、IME、光标、尺寸变化、窗口取消和 ownership fence。若要求重写 Xserver 或模拟通用 DRM，退出该路线。

验收：描述“在哪一段减少了哪次复制”，给出端到端收益和适用集合。保持旧客户端/旧服务器安全协商与完整 GPU Copy 回退；未通过完整窗口语义验收不得进入默认。降低一段 Copy 不能自动宣称端到端零拷贝或整机节能。

## 13. T8：应用覆盖与 WebKit 专项

入口：`scripts/gpu-run.sh`、`src/webkit-gpu-policy.c`、`scripts/trae-start.py`、桌面/CLI 迁移脚本、现有 launcher stub 测试。

### 必做：按真实应用建立覆盖矩阵

优先 Chromium、当前助手、Trae、CC Switch，再按用户实际安装/使用加入 Office、GTK/Qt 程序。每行记录应用/框架版本、启动入口、实际后端、GPU 进程、CPU 剩余工作、传输方式、通过场景、限制与硬件回退。未运行的应用标记未确认，不凭桌面继承环境判定全部硬件化。

- 原生 Skia 为现有默认；单应用不兼容时保留 `PAD_GPU_SKIA_BACKEND=angle` 硬件回退，不能全局换后端。
- 若冷启动或首帧卡顿落在 shader/pipeline 编译、图片上传或资源分配，先区分冷/热缓存，核对已有缓存是否失效或重复创建；只修已证实的重复工作，缓存必须有界并与驱动/应用版本匹配。不额外预热整个桌面，也不默认增加后台编译线程。
- GTK4/Qt Quick 等若应用自身支持硬件后端，先验证该版本已有接口；传统 GTK/Qt Widgets/Office 不保证相同覆盖。禁止将某一框架变量写进整个桌面环境。[GTK 官方运行说明](https://docs.gtk.org/gtk4/running.html)
- 应用内主线程、语法分析、插件或 JS 热点单独记录；没有图形热点时不修改 GPU 栈。优先上游修复/稳定版本与单应用可撤销配置，不维护 Chromium/Electron 大型 fork。
- 验证 locale、URL/文件参数、单实例、用户配置、输入法、剪贴板及窗口实际可见。所有正常入口继续 gpu-run；兼容修复有版本/能力适用条件与删除条件。

### 条件性：WebKit 的 SHM 传输

先在 CC Switch 实测 WebProcess/UIProcess/GPUProcess 的 CPU、读回/上传和拷贝量，确认是否是主要热点；检查 always policy 是否造成无收益的后台工作。不能直接关闭现有硬件策略。

按安装版本阅读 WebKit 上游渲染与共享缓冲接口，先检查可用的标准导入路径；DMA-BUF、GBM、AHB 的布局与同步不是同一种契约，不能只去掉 FORCE_SHM 就宣称可用。[WebKit 图形架构](https://docs.webkit.org/Ports/WebKitGTK%20and%20WPE%20WebKit/Graphics.html)

只有 CPU 传输成本显著、共享格式/句柄/同步可行且改动能局部维护时，才建立独立 WebKit 构建原型；不更换系统 WebKit 库，不让 LD_PRELOAD 扩散到 Android linker 或其他程序。若只能靠长期大 fork，保留现有 SHM 并记录能力边界。

验收：目标应用实际交互正确，后端证据完整，CPU/能耗收益大于新增提交/同步成本；既有 SHM 硬件路径始终可回退。软件只在用户明确请求下启用。

## 14. T9：视频硬解的独立可行性阶段

这是媒体栈扩展，不是给 gpu-run 增加一个参数。先记录常用播放器/浏览器、编码、分辨率、帧率、是否软件解码和实际热点；没有重要视频需求时可保留为未实施，不阻塞图形交付。

执行顺序：

1. 在 Android/bionic 侧使用公开 NDK MediaCodec 接口做隔离、按需启动的原型，验证硬件 codec 名称/能力及真实解码；服务/命名空间条件正确，不全局预加载 bionic 到 glibc。[Android NDK Media](https://developer.android.com/ndk/reference/group/media)
2. 先验证一个固定 SDR 视频的解码、PTS、seek/flush、EOS、错误、资源释放，再研究 Surface/AImageReader/AHB 输出与 GPU 消费的兼容性。格式/颜色/同步或受保护内容不支持就明确拒绝。
3. 选择一个应用适配边界最小的 Linux 消费端，验证传输成本、音画同步、掉帧、CPU 与能耗；不同时改播放器、FFmpeg、Chromium、WebKit。
4. Linux 浏览器接入需单独确认其媒体后端接口与构建维护成本。独立解码器成功不能写成浏览器已硬解。DRM、HDR、所有 codec、编码与视频会议不作首期承诺。

退出条件：数据回传/色彩转换抵消收益、需要系统修改、缺少稳定消费接口、持续大 fork 成本不合理。首期产物可以是有证据的“不进入开发”，不能把不可行原型混入正常启动链。

## 15. T10：能耗、性能与资源验收

入口：T2 修正后的现有采样器、`docs/benchmarks.md`、原始 CSV 与脱敏 evidence。下面是**拟定的验收规则，不是当前已达到的成绩**。

### 指标和判定

| 维度 | 要记录的指标 | 推广规则 |
|---|---|---|
| 正确性 | 受控图案像素、颜色空间、遮挡/输入/恢复 | 可复现新增错误为阻断项，不用平均 FPS 抵消 |
| 帧质量 | 可靠呈现间隔 P50/P95/P99、最长停顿、样本数/丢失率 | 连续动画/滚动场景评价；静止页不要求 60 新帧；长尾不显著恶化 |
| 响应 | 有因果标记的输入→对应提交/显示 | 标明测量终点；缺物理显示证据不写 input-to-photon |
| CPU/GPU | 各进程 CPU s、CPU/等量工作、GPU 阶段耗时 | 不拿减产帧或换成低质量画面当效率提升 |
| 搬运 | 各阶段 CopyPixels/理论字节、draw/submit 次数 | 是工作量指标，不冒充实际 DRAM 流量或瓦数 |
| 空闲 | 相关线程唤醒/CPU、无更新时的提交来源 | 清除可避免自激工作，保留真实输入/光标需求 |
| 能耗 | 单位任务耗能、同条件平均功率、温度与区间 | 单次短样本不宣称节能；不能用整机电流归因某应用 |
| 资源 | RSS、FD、AHB/图像/region 等可观测数量、GPU 进程重建 | 允许有界缓存；重复同任务应趋稳，不持续无界增长 |

先做相同基线 A/A 估计噪声，再为该任务锁定改善目标和非退化容差，不在看到结果后改门槛。建议仅在拟推广的优化上进行至少三组交替 A/B；报告各组与中位结果、波动范围。改善若未超出观测噪声，标记“收益未证明”，保留较简单版本。样本不足时不强调 P99 或长期稳定。

60 FPS 连续动画的理想节拍为约 16.67 ms；目标是减少不必要的跨节拍停顿，不要求任意页面所有阶段都恒定小于这个数。轻载场景的改善不能掩盖全页滚动、多个应用或热状态下的退化。

### 测试预算

1. 每个候选先运行受影响的 stub/纯逻辑/像素回归，只做一个短实机冒烟。失败直接定位，不重复全矩阵。
2. 只有进入推广的候选才测固定静止、滚动、输入三个代表负载；其他场景按改动范围追加。不做版本×模式×应用×尺寸的全排列。
3. 能耗先确认电池节点单位、正负号、放电状态与采样精度；同亮度、分辨率、面板模式、软件/页面、网络和相近温度/SOC。建议暖机约 5 分钟、每段 10–15 分钟，必要时三组交替；无法稳定控制的样本标无效。
4. 初步稳定性使用 30–60 分钟混合操作；发布候选再进行一次约 2 小时实际工作与恢复观察。不能把这些时长写成全天稳定性证明。下一次出现新故障再定向延长。
5. 不为本计划重新做软件渲染对照，除非用户明确请求。优化基线是当前正常硬件栈；不把 r3.3 的历史收益重复计入新版本。

原始数据不可改写；每条结论附条件、版本、样本量和缺失项。测试通过且无新风险时交付，不因追求“绝对极限”无休止测量。

能耗优先按同一完成任务比较；电流/电压换算单位后按真实采样时间积分得到能量，报告采样间隔与误差来源。应用进程 CPU、整机放电与可用 power rail 分列。浏览器产帧变多造成每秒 CPU 上升时，同时报告单位任务/有效内容帧效率，不能选择有利分母隐藏功耗或质量变化。
