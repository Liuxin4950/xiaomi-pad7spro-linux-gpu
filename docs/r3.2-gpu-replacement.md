# r3.2：替换 r2 的实际 GPU 桥接

> 历史阶段记录。当前默认已为 r3.3；以下日期、版本和实测数值保留，不作为当前配置指令。请先读 [CURRENT-STATE](CURRENT-STATE.md)。

2026-10-12 已安装、切换默认入口。版本目录为 `/opt/pad7spro-gpu-observe-20261012`，`release.json` 标识为 r3.2；目录名是本次独立构建时确定的名称，不代表默认开启诊断。`/usr/local/bin/gpu-run` 和 `gpu-launcher` 已指向该目录。r2、原始 r3 的目录和二进制保留。

## 已实施的渲染与路径改动

实际路径是 Chromium/Electron 的 GPU 光栅化和合成 → ANGLE Vulkan → sysvk/libhybris → 原厂 Mali → AHB/WSI → Termux:X11 GPU Present → Android 显示。没有使用 llvmpipe/lavapipe 替代 Mali；仍需要 CPU 执行 JavaScript、布局、调度和驱动提交。`--enable-gpu-rasterization` 明确启用硬件光栅化，冲突的 `--disable-gpu-rasterization` 被启动器拒绝。

- **Copy 命令复用**：保留原始 r3 的每图像两次录制（初始化与稳定布局），后续复用；上一帧 Fence、渲染信号和 X11 Idle 的安全条件保留。此前定向测试中 300 次录制降至 8 次，详见 r3 审查。
- **空闲休眠**：保留 FIFO 无新帧时阻塞等待、退出显式唤醒的改动。
- **Complete 先到、Idle 后到的修复**：旧代码在 Complete 清空队列后可能停止读取尚未到来的 Idle，使 Acquire 无法取得已释放缓冲。新增每图像 Idle 状态及实际 Acquire 等待者计数。仅有等待者需要释放缓冲时继续监听，静止画面的前缓冲不会造成周期轮询。旧二进制确定性复现失败，新二进制通过同一复现和生命周期回归。这是已证实的代码错误，但不能据此宣称历史 410 ms 就由它造成。
- **固定节奏的限帧**：FIFO 与 MAILBOX 均保留 60 fps 提交上限。每次唤醒后从上一截止时间推进，跳过已过期时隙，避免 `now + interval` 把每次调度误差逐帧累积。先前 r3.1 用 RandR 宣告频率来决定取消 FIFO 上限，但旧 Termux:X11 的宣告值并不限制真实 MSC 时钟，因此该策略已撤回；不能为减少等待而放任超过目标帧数的 GPU 工作。没有降低分辨率或默认改成 30 fps。
- **常用入口统一**：Trae 系统菜单、新窗口和 URL Handler 原来直接执行程序，已改为统一 GPU 入口。桌面图标、Chromium 和 ChatGPT 入口跟随默认版本。
- **默认没有逐帧诊断**：GPU 时间戳和有界时间线只有 `PAD_GPU_WSI_TIMELINE_DIR` 设置时创建；正常使用不分配 QueryPool、不写逐帧日志、不写 trace_marker。

## 真正使用 GPU 的证据

独立 Chromium 和 Trae 均取得运行时 `SystemInfo.getInfo`：渲染器是 `ANGLE (ARM, Vulkan 1.3.278 (Mali-G925-Immortalis ...))`，GPU compositing、Canvas、WebGL 和 rasterization 已启用，`processCrashCount=0`。Trae 在新启动器下 `rasterization=enabled_force`。GPU 进程同时映射新前缀的 WSI/sysvk 与 `/vendor/lib64/hw/vulkan.mali.so`。不是仅凭启动参数认定 GPU。

全分辨率 3200×2054 Vulkan 动画完成 300 帧，正确退出；AHB 分配、跨 socket 传递、回读与释放通过。补丁从锁定原始提交重新应用，与编译用源码逐字节相同；WSI 生命周期、取消、断连、BGRA、旧 Swapchain 与新释放顺序回归通过，27 项启动器测试通过。

用户重启桌面后，当前 ChatGPT 主进程 PID 24303 已恢复 Mali GPU。为加载最终限帧修正，仅重连其 GPU 子进程（24358→15164），主进程及会话保留，新子进程映射原厂 Mali 与更新后的 WSI。一次 GPU 子进程重启是本次主动操作，有单独记录；不能把对应 crash-count 当作未知崩溃。旧 PID 16569/29514 的软件回退状态已经结束。

## 可比的帧处理数据

同一客户端、1280×800、持续变化、60 次/秒生产、300 帧，屏幕点亮、Termux:X11 在前台，CPU 时钟与 SF 时间以 MONOTONIC 为基准，记录 BOOTTIME/REALTIME 配对。这里的帧处理时间是应用 Acquire→提交完成，不是屏幕光子延迟。

| 指标 | r2 | r3.2（固定节奏，保留 60 上限） |
|---|---:|---:|
| Acquire P99 | 11.649 ms | 1.777 ms |
| 应用帧处理 P50 | 1.982 ms | 1.715 ms |
| 应用帧处理 P99 | 14.102 ms | 4.951 ms |
| 应用稳态 CPU | 138.04 ms CPU/s | 158.06 ms CPU/s |
| SF 层实际 present 间隔 P99 | 25.06 ms | 33.26 ms |
| 本轮 SF 最大间隔 | 33.45 ms | 41.69 ms |

因此可以证实减少了应用/WSI 等待，**不能声称本轮整机 CPU 显著下降或屏幕卡顿已经彻底消除**。SF 尾部未同步改善，是剩余工作。SF ring 中的实际 present fence 表示整个 Termux:X11 层提交；本轮持续动画中每秒约 65.5–68.6 个呈现，而客户端每秒约 60 帧，含额外/重复内容，不能把它当作新画面 FPS。

先前同一 480 帧/8 秒客户端中 r2、原始 r3、释放修复版的应用帧处理 P99 分别为 15.77、15.54、15.10 ms：仅命令复用和释放修复不会自动解决双重节奏等待。该首轮 CPU 汇总误包含采集子进程，已弃用 CPU 项；后续表格使用独立客户端 `/proc/PID/stat` 统计。末尾退出 CPU tick 可能遗漏，分辨率为 10 ms。早期静止测试开始 1.5 秒之后，r2/r3.1 客户端均为 0 CPU tick；旧周期唤醒减少是真实实现，但不能在这个短窗口声称巨大整机 CPU 收益。

## GPU 搬运成本和功耗边界

3200×2054、应用渲染 Fence 预先完成的单独测量：Mali GPU 时间戳记录桥接 transfer 窗口 P50 **1.151 ms**、P95 **2.857 ms**、P99 **3.744 ms**，最大 7.037 ms。窗口包含转移与布局/所有权屏障，不是 CPU Fence 时间，也不是完整 Android 合成时间。GPU 原始时钟没有校准到 CPU 绝对时间，只报告持续时间及 CPU 围栏边界。

保留 BGRA optimal 渲染图像 → RGBA AHB 字节 Copy；Termux:X11 还将 AHB 拷入屏幕 pixmap 并呈现。命令复用减少 CPU 录制开销，不减少这些 GPU 搬运字节。3200×2054 的一次完整读+写约 52.6 MB，60 fps 的理论读写字节量约 3.16 GB/s，实际缓存/压缩/总线流量未测。继续缩减 Copy 需要改变双方图像/字节格式或正确跟踪逐缓冲 damage；不能直接关闭 Copy、假称零拷贝，否则会破坏颜色和缓冲内容。本次没有这样改协议。

另外用相同 Chromium 文本滚动页面运行各 6 秒，硬件模式的应用进程 CPU 合计 **2.76 s**，显式软件模式 **6.20 s**（约减少 **55.5%**）。运行时分别证实硬件合成/光栅化启用与全部软件渲染。这个结果只覆盖该页面的浏览器进程 CPU，不包含 Android/Termux 的 CPU，也未逐帧核对两组实际新内容呈现；它不是整机耗电或续航提高 55.5% 的证据。视频解码和编码目前仍为软件，不应宣称所有视频负载都已硬件化。

没有调高 GPU/CPU 频率、关闭 thermal、屏蔽系统服务或修改 SELinux。电量、电流、亮度、温度和后台状态尚未完成稳定可比的耗电评估，因此实际续航提升仍待验证。

## 系统异常的确定根因与已完成的规避

`com.miui.daemon` PID 6911、进程 start_ticks 17842 保持不变。原厂 MiuiDaemon 2.2.2 的反汇编和数据库记录共同证明：一条 KernelSU 安装检测事件 `ty=388` 的 `subclass=NULL` 被映射为异常类型；`Utils.getClassByType()` 对它直接调用 `String.contains()`。异常使上传完成清理无法执行，外层 `CoreEventUploadService` 对仍未完成的队列连续重试，没有退避。

15 秒独立进程采样取得 1735 次异常（约 115.7/s），daemon 消耗 17.12 CPU 秒（约 1.141 CPU s/s），上传线程与 GC 是主要消耗。准备 SQLite 在线备份、在副本完整删除/恢复校验后，只将这一条坏记录移出活动队列，原记录和完整备份保留。其他记录的事务内摘要不变，DB/journal 的 UID/GID/权限/SELinux 标签不变，没有冻结、卸载、禁用、重启 daemon。

修复后相同 PID/start_ticks 的 30 秒采样为 0 异常、0 daemon CPU tick；切换新桥接和启动应用期间的独立采样也为 0。直接触发点是固件处理 malformed 设备监控事件的错误，不是 GPU 栈中的函数。这个同进程、单记录干预提供因果证据；仍不能重建最早事件形成时间或证明任意 Linux 操作永远不可能间接影响固件事件。

这是有备份的队列规避，不是固件永久修复。系统更新/Root 组件重新安装等再次产生同类坏记录时可能复发；必须由小米在 null 处理、队列失败清理和退避上修复。私有完整证据位于 Android `/data/local/tmp/pad-gpu-root-cause-20261012/quarantine-plan` 及仓库忽略目录 `build/root-cause-20261012`，APK/dex/系统 DB/个人日志未提交。不要用整个旧 DB 覆盖现在的 DB；确需回滚只恢复保留的那一行，且会重新触发异常循环。

旧 409.705 ms 的样本中 Acquire 占 387.433 ms、Present 调用约 2.088 ms，另有客户端 20 ms 暂停。它是应用请求更新时的等待，不只是主动空闲。但旧 Perfetto 不覆盖该时段，屏幕可见状态未可靠记录，故无法证实它是可见掉帧，也无法与 daemon 异常建立时间因果关系。

## 本次重开后的单核与约 5 W 问题

新桌面中独立进程和线程统计显示：占满核的是搜狗输入法 PID 9163，约 1.3 个 CPU 核；其中主线程约 93%，GC 线程约 37%。daemon 没有复发。键盘已经隐藏 (`mInputShown=false`)，仍持续消耗。电池为 Discharging，1.12 A × 4.324 V ≈ **4.84 W**，与用户反馈相符。短暂焦点重连无效。

两次低频 simpleperf 的实际 Java 调用链为 Sogou `onUpdateCursorAnchorInfo` → `HardKeyboardServiceImpl.updateCursorAnchorInfo` → `android.app.Thientead.substring` → 多层 Xposed HookChain，CPU 热点包括 LSParanoid 字符串解码、堆栈遍历/生成和 GC。仅 HyperCeiler 模块在搜狗作用范围中启用，进程实际映射其 APK。已确定忙碌执行进入该 Hook 链，但没有完成去除 Hook 的 A/B，因此具体哪项增强及其因果作用仍需验证。

同时修正了旧 Termux:X11 的输入法协议：mode=0 取消监控时不再反向发光标回调，MONITOR 只在位置变化时报告，不支持的几何过滤器返回 false。新前端 APK 已安装，签名与原包一致；四个原生 GPU 库逐字节不变，Linux X server PID 23811 和 ChatGPT 主进程均保留。它修正了实际代码错误，**但安装后搜狗仍约 120–130% CPU，整机仍接近 5 W**，不能把它说成这个满核问题已解决。

已向用户请求暂时只取消 HyperCeiler 对搜狗的作用范围并短暂重启搜狗。它保留输入法和数据，但会改变用户的模块增强设置；得到确认之前没有改模块范围、偏好、禁用输入法或停止它。随后两次 10 秒、8 秒采样中，搜狗同一 PID/start_ticks 均为 0 CPU tick，主线程在 `do_epoll_wait`，cgroup `frozen=0`；模块设置仍为原值。两窗放电读数均值为 3.37 W、3.35 W。当前异常已经停止，暂不改模块范围。因为不是隔离变量的长期试验，不能把回落单独归功于某个补丁，也不能证明输入操作后不会复发；完整稳定性与续航目标仍未证明。

## 证据、回退和剩余工作

公开脱敏汇总为 `evidence/r3.2-replacement-2026-10-12.json`。原始运行证据保存在 `build/live-replacement-20261012`；`reopened/phase-capped-final` 是最终固定节奏 A/B；`paced-validation` 是已撤回的去除 FIFO 计时器实验；`display-quick` 是首轮 A/B/C 与普通 X11 PutImage 场景。普通 X11 测试无 Vulkan 桥接，但含 CPU 画图和 X11 传输成本，不等价于零成本显示基线。开始的 MIT-SHM FD attach 被服务器拒绝，未当作成功测试。

入口和菜单原内容备份在 `build/live-replacement-20261012/activation-backup`。仅回退默认 GPU 版本可原子替换两个 symlink，使它们重新指向 `/opt/pad7spro-gpu-dev-20261007-r2/bin/gpu-run`、`gpu-launcher`，再重开应用；没有必要移除新版本或恢复错误的 Trae 入口。不要覆盖已经加载的库。

当前 ChatGPT 硬件恢复已经完成。还需要检查真实输入操作时的应用帧到 SF 的关联，定位 SF 重复呈现/尾延迟和 BufferQueue，进行稳定条件下的电量/热量比较及锁屏恢复验证。没有完成 X11 完全关闭的对照，也没有为了补齐这项数据而结束用户桌面或重新引入坏系统事件。当前默认替换已完成；“所有卡顿消除、整机功耗/续航达标”的完整目标尚未证明。
